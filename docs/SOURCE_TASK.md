3. **不使用子代理**，除非用户之后明确授权。允许使用当前环境直接提供的本地工具、官方 CLI、图像生成技能和自动化测试工具；不得以此为理由启动其他自治代理。
4. 按本文件的阶段依赖持续执行：**发现 → 设计 → 生成素材 → 构建场景 → 完成玩法 → 测试 → 修复 → 视觉打磨 → Android 验收 → GitHub 同步 → Release → 发布复核**。

## 1. 项目定位与明确范围

### 1.1 产品体验

- 定位：可爱、轻松、治愈、明亮而克制的 **2D 休闲益智小游戏合集**。
- 主要使用情境：手机竖屏单手或双手操作，随时打开玩 2–5 分钟，随时退出，没有操作负担。
- 八款游戏必须在同一主程序内共存，彼此是**独立 Godot 场景和独立状态机**，不是八个 APK、八个 WebView 或八次外部应用跳转。
- **八款从首次安装起全部可选**。允许个人纪录、轻度收集和解锁外观，但禁止用长时间养成或强制关卡解锁阻碍体验。
- 默认完全离线；不需要注册、登录、联网、云存档、广告、内购、排行榜服务器或额外运行时 AI。
- 没有强制体力、每日签到、倒计时焦虑或刻意高难度惩罚。玩家随时可重试。
- 美术、动画、音效是本项目**一等需求**，不是最后填充的装饰品。

### 1.2 明确不做

- 不做 3D 城市、多人联网、复杂 AI 对手、复杂 Roguelike、冗长故事、付费广告系统或大型自制引擎。
- 不增加第九款游戏；不擅自替换已确定玩法。
- 不用真人写实、浓重赛博霓虹、廉价素材拼贴、杂乱扁平按钮或未经处理的默认 Godot 控件作为最终视觉。
- 不直接盗用《水果忍者》《合成大西瓜》《泡泡龙》《羊了个羊》等商业游戏的角色、插画、音乐、Logo、商标或关卡资源。仅借鉴通用玩法规则，并产出**原创**游戏命名、美术、音频与关卡。
- 不以截图、展示动画、无法操作的假 UI 或作弊模拟状态代替真实游戏逻辑。

## 2. 必须交付的八款游戏与逐项玩法验收

下面是**确定阵容**，名称是项目内的暂定英文名称，允许为避免商标冲突作小幅命名修正，但不可改变玩法类别。每款至少包含：入口卡片、首次简短提示、完整输入、分数/关卡、暂停、重开、成功/失败或无尽模式结算、离线进度保存、音效与动画。

### G01 · Fruit Drop（水果合成 / 合成大西瓜类型）

**循环**：屏幕顶部移动投放点 → 松手落下水果 → 相同等级的圆形水果接触后融合为更高等级 → 继续合成冲击纪录 → 堆到危险线才结束。

- 使用稳定的 2D 物理、圆形碰撞体、边界和重力，投放前显示下一颗水果和落点预览。
- 合成事件必须幂等：一个水果同一时刻不能被多个碰撞重复合并、重复加分或生成多个结果。
- 同级合并的大小、分数、层级明确；增加合成回弹、表情变化、短粒子和彩色波纹，但不遮挡操作区。
- 顶部溢出判定使用适当宽限，避免刚投放的物体瞬间误判失败；防止水果永久卡住或飞出场景。
- 验收：可从初始状态玩到高等级合成，可出现自然失败，可立刻重玩，多次快速连锁合成无异常。

### G02 · Bubble Garden（泡泡龙）

**循环**：从底部拖动瞄准 → 松手发射彩色泡泡 → 碰撞贴附六角错列网格 → 同色达到阈值消除 → 失去顶部连接的泡泡掉落 → 清屏过关。

- 提供瞄准参考线、墙壁一次或多次反弹的可视化提示，以及下一发预览。
- 同色消除建议阈值 3；网格吸附稳定，不允许泡泡重叠、越界或在网格缝隙穿透。
- 处理顶部连通性和悬空泡泡批量下落，连锁反馈必须清楚。
- 发射颜色池应与场上存量颜色合理联动，避免因继续产出已消失颜色导致软锁。
- 早期关卡短而愉悦；后续逐渐变复杂但不刻意折磨玩家；提供重新开始、简单辅助与提示。
- 验收：直接射击、墙面反弹、三连、悬空掉落、清屏、失败/重开全部真实有效。

### G03 · Cake Stack（堆叠高塔 / Stack 类型）

**循环**：一层蛋糕/软糖平台在水平方向来回移动 → 玩家点击定格 → 对齐部分保留，多余部分切除并掉落 → 连续完美堆叠触发奖励 → 越叠越高。

- 极其简单的**单次点击**操作；移动速度随高度温和增加并有合理上限。
- 精确判定重叠宽度；完全错过即结算；不能出现宽度负数、位置累计漂移或穿帮。
- 完美判定设合理容差，连续完美时出现平滑吸附、音阶递进和短暂轻庆祝。
- 镜头跟随、动态背景、平台切边掉落与连击反馈是本游戏重点。
- 验收：高度累加可持续，失败必可到达，无尽成绩和最高纪录正确。

### G04 · Bouncy Balls（多弹珠打砖块 / 挡板接球与分裂）

**循环**：底部拖动挡板接球 → 弹珠撞击砖块、边墙、弹跳装置并反弹 → 特殊倍率门产生更多球 → 同屏多球连击清砖 → 进入下一阶段。

- **采用用户描述的挡板接球版本**，不能偷换成单纯拖动发射一串球后等待回收的版本。
- 挡板移动必须跟手并限制在屏幕内；弹球碰撞速度可控，避免穿砖、卡墙、无限横向弹跳。
- 制作 ×2、×3 增殖门、不同耐久砖、适量特殊弹跳与炸裂反馈。倍率不是简单分数文字，必须真实影响球数。
- 设计**严格的同时球数上限与对象池**，超额产生时以可解释的分数/能量反馈代替无上限实例生成，保证中档 Android 手机流畅。
- 所有弹珠丢失后正确结束或启动新的球；清场可进入下一波；暂停、返回后不遗留幽灵碰撞体/音效。
- 优先打造多球连撞时的爽感和可读性，不要引入复杂肉鸽数值系统。
- 验收：能准确接球、连续反弹、击砖、分裂、多球回收、失球、过关和结算，压力测试不出现球数爆炸或帧率崩溃。

### G05 · Tile Trio（三张消除 / 羊了个羊式配对）

**循环**：点击可见且可选的图块 → 放进底部托盘 → 三个同图案自动消除 → 清空叠层图块即通关；托盘满则失败或进入宽容补救。

- 图块有真实遮挡关系、可选状态、选择反馈、三连消除动画；建议托盘容量 7，难度不应照搬极端高失败率设计。
- **关卡可解性是强制条件**：从可逆的构造过程生成关卡，或使用经求解器验证的固定关卡，不得单纯随机堆出大量必死局。
- 合理分层、图案配比、撤回与轻量提示；撤回/提示不能依赖付费或广告。
- 每个关卡有明确终局。托盘满、反复点击、快速三消时不得吞图块、复制图块或卡死。
- 验收：有可复现的求解测试，至少抽样多批种子验证可解；能实际连过多关且失败可以快速重试。

### G06 · Mochi Hop（麻薯跳跳乐 / 微信《跳一跳》式蓄力跳台）

**循环**：一个圆滚滚的麻薯小角色站在当前甜点跳台上 → 玩家**长按屏幕蓄力**，角色逐渐压扁 → **松手后向前方下一块平台跳跃** → 成功落地得分、靠近中心得到奖励 → 新跳台出现并平滑推进镜头 → 不断挑战最高分；落空则结算并立即重玩。

- **严格保留“长按蓄力 → 松手起跳 → 落到下一个平台”的核心**，不能误做成自动跳跃、点击即固定距离跳跃、跑酷闯关、向上无限跳平台、两次点击选择角度或复杂方向操控。触摸游戏区域即可蓄力；按住时间越长，跳得越远，映射关系稳定、可学习、有合理上限。
- **采用 Godot 纯 2D 场景制作精美的 2.5D 伪等距视觉**：可用菱形/圆角立体感跳台、上表面落点区域、侧面阴影与分层精灵、局部透视和投影。不必创建 3D Mesh、3D 物理和复杂自由相机；规则计算使用可测试的 2D 世界坐标、可预测抛物线与确定性落地判断。
- 跳跃方向由下一平台相对于当前平台的位置决定（可在两个对角方向间变化），玩家只控制**按住时长**。跳台随机生成必须与最小/最大蓄力距离、平台宽度、投影规则配套；**每块平台必须有实际可命中的蓄力区间**，禁止程序生成根本无法跳到的组合。
- 跳跃手感优先：蓄力轻微下压、底座压缩、小幅蓄力音调变化；起跳拉伸、空中弧线、柔软落地回弹、平台微晃与细小糖粉粒子。为确保手感，空中位置与影子/落脚点分离，**仅用脚下投影落点和平台顶面可落区域判定**，不能以精灵画面碰到平台侧面就错误判定成功。
- **默认宽容而有成就感**：早期平台较宽、间距偏近、蓄力甜区宽；合理允许边缘安全余量和轻微落点吸附（阈值明确且可测试）。逐渐提高挑战但设置难度上限；不要做过于苛刻的像素级判定、倒计时和频繁死亡惩罚。
- 命中平台得基础分；**中心完美落点**给予清楚的短暂加分和柔和连击音阶。采用本项目原创计分规则，不照搬原游戏特殊商家平台、形象、UI 或隐藏分数机制。持续保存本局分数、历史最高分；失败显示本局/纪录与一键重试。
- 视觉主题优先采用**麻薯小动物 + 马卡龙、棉花糖、布丁和软糖漂浮跳台**；摄像机轻柔跟随，让下一个目标始终可见；场景保持简洁、构图有呼吸感，严禁过度背景杂物掩盖落点。AI 生图只提供原创角色/跳台素材，不能直接拼贴微信《跳一跳》的原角色或商标。
- 输入生命周期必须稳健：触控按下/释放、蓄力中暂停或返回、来电/后台切换、快速连点、多指误触、跳跃过程的重复输入、场景卸载，均不能产生幽灵蓄力、重复跳跃或失控状态。桌面鼠标按住/松开可以作为开发调试输入。
- **验收**：短按、正常按、长按三种距离可预测；中心/边缘成功落地、落空失败、连击计分、镜头跟随、游戏结束/即时重玩、最高分保存均真实运行；批量测试随机平台的可达性，在不同屏幕比例和帧率下相同蓄力时间得到一致的物理结果，无必死跳台、视觉落点与规则判定脱节。

### G07 · Number Bloom（2048）

**循环**：上下左右滑动移动整个 4×4 棋盘 → 相同数字沿移动方向合并一次 → 有效移动后产生新数字 → 冲击 2048 和更高成绩。

- 严格实现标准 2048 合并顺序；**同一格一次移动中只能合并一次**。
- 无效滑动不能新增数字；仅在成功移动后投放新格；生成概率记录、可测试且合理。
- 提供撤回一步、重新开始、继续游戏、达到 2048 的胜利提醒、无合法移动时游戏结束。
- 动画、方块缩放、分数弹字与颜色层级统一；数字可读性不得因高等级颜色下降。
- 验收：针对典型行列 `[2,2,2,2]`、`[4,4,8,8]`、满盘、空格、无效滑动等测试正确，重进游戏纪录仍在。

### G08 · Jelly Slice（可爱切水果 / Fruit Ninja 类型）

**循环**：果冻水果从下方或侧方抛出 → 玩家用手指连续滑过进行切割 → 命中产生两半、果汁粒子与连击分数 → 继续挑战或轻松游玩。

- **默认有 Zen/禅意模式**：无炸弹或强制惩罚，可以一直切、随时退出；可选加入温和的限时挑战模式。
- 用触控滑动路径的线段扫掠/连续碰撞判断命中，不能只凭单帧触点导致快速划过时漏判。
- 为每种果冻水果准备原创完整态与两半切开态，采用预制切面/动画即可，**不要求复杂实时网格切割**。
- 同一水果只能切一次；连击窗口、重叠轨迹和粒子触发要可靠；不能因为多指滑动/快速切割而崩溃。
- 验收：单切、多切、连续划线、快速划过、漏切、离屏回收、结算与重启均流畅。

### 八款共用的硬性玩法要求

- 主菜单一键进入，单款游戏返回主菜单不超过两次明确操作。
- 每款都提供首次轻引导，5–15 秒内可以真正开始玩，不用阅读多页教程。
- 玩家失败后有清晰提示和立即重玩按钮，禁止转圈等待、陷入死局或逼迫看广告。
- 单款游戏至少有一种完整的可持续游玩机制：**经验证的多关卡**或**有纪录的无尽模式**，而非“打通第一关就没内容”。
- 动态随机玩法要支持可记录的 seed，便于复现错误和自动化验证。
- 音乐/音效开关、低特效或减少动态效果、暂停/恢复、保存/重启等基本行为一致。

## 3. 技术架构及平台要求

### 3.1 技术选择

- **优先使用 Godot `4.7.2.stable` + GDScript（非 C#）**，并安装完全匹配的官方 Android export templates；如目标环境已固定一个更新且确认为稳定/兼容的 Godot 版本，可采用它，但必须记录版本和兼容性原因，不得使用不稳定 nightly 来凑功能。
- 只开发一份 Godot 工程，使用 2D 节点、Control UI、可复用动画和必要的物理系统，不构建原生 Android Activity 混合架构或独立网页前端。
- Android **竖屏**设计；建议设计分辨率 `720×1280`（高质量素材可按 1080×1920 制作），采用适合 2D 的 `canvas_items` 及 `expand` 策略，真正适配不同高宽比、安全区、打孔屏/刘海、系统返回手势区域。
- 根据实际支持的机器选择 Godot 的 **Compatibility** 渲染器作为优先兼容方案，若实际设备测试证明更合适可调整。不要仅凭桌面显卡运行良好断言 Android 渲染无问题。
- 以官方 Android 导出文档配置 JDK/Android SDK（优先 JDK 17）；验证 SDK、Build Tools、platform-tools、export templates、`adb` 与 `gh` 工具可用。
- 输出 APK 优先覆盖常见 **arm64-v8a** 手机；兼容更多 ABI 的决定应根据 APK 体积、设备和当前导出方案验证。包名必须稳定、合法、与账户/仓库不冲突。
- 如有必要，提供 Windows 桌面测试模式方便快速运行与截屏，但**唯一正式交付平台仍是 Android APK**。

### 3.3 共用系统

1. **Home**：精心设计的原创图标、八张游戏卡片、最高成绩/关卡摘要、Settings 入口；滑动和点击响应迅速，不能成为简单文字列表。
2. **GameShell**：一致的返回、暂停、重玩、成绩、帮助入口与结果面板；不遮挡操作区域。
3. **SaveManager**：`user://` 本地持久化，版本号与升级迁移；合理防损坏写入（临时文件/备份/异常恢复），重启后保持设置和记录。
4. **AudioManager**：统一控制轻柔 BGM、SFX、音量与静音；切场景不重复播放多层背景音乐；尊重静音与暂停。
5. **Motion/Haptics**：统一缓动曲线、时长与触觉反馈，可关闭/减弱特效；仅在设备支持时进行轻微振动，不请求不必要的权限。
6. **Settings**：至少有音乐、音效、减少动画、语言（可实现简中 + 英语）和重置纪录的安全确认。语言字符串集中，README 保持全英文。
7. **App Lifecycle**：系统返回键/手势、任务切换、进后台、恢复、异常退出、屏幕尺寸变化，都有明确可恢复策略；不得误丢当前游戏状态或因长时间后台运行错误累积计时。
8. **Accessibility**：可识别文字和按钮，触控目标建议不小于约 48dp 等效区域，避免色彩是唯一玩法线索；重要状态同时具有形状、符号或文字提示。

## 4. 美术总监级设计要求：本任务最高优先级

### 4.1 统一世界观与视觉基调

设计一款像“一盒精致的软糖玩具与温暖文具”一样的应用：**cozy / kawaii / pastel / soft 2D / friendly / polished / playful**。

- 主题基调：奶油白、浅桃粉、薄荷绿、淡黄、天空蓝、浅紫；可以有局部强调色，但禁止喧闹的高饱和荧光大面积铺满。
- 背景轻盈留白，内容区清楚分层；柔和圆角、轻纸感/果冻感、适量软阴影、有质感的图标与饰件。
- **2D 卡通插画**而非逼真 3D、廉价纯几何占位图、糊状 AI 贴图或未经统一处理的多来源资产；Mochi Hop 可以在 2D 节点中绘制柔和的 **2.5D 伪等距跳台**，这不改变项目“纯 2D Godot 工程”的技术边界。
- 八款共享一套颜色 token、字体、描边厚度、阴影范围、按钮形态、粒子风格、音效音量、弹性曲线与过渡规则。
- 各游戏主题变化仅体现在主色、角色/物件和小幅插画细节上；玩家从任一游戏退出仍感觉在同一个应用。
- 提供正式 Android 启动图标、启动屏、主菜单动态卡片图标、背景、结果面板、设置页和必要的空状态。

### 4.2 必须主动使用 AI 图像生成能力

1. 先检查本地 Codex 是否安装**可用的 AI 生图技能或工具**（例如用户已配置的 image generation skill、图像生成 API、相关创作工具）。**若存在，必须读取其实际说明并调用，不得只在报告中写“使用了 AI 美术”。**
2. 先生成 **2–3 个风格方向的主菜单/游戏内概念参考图**，对比色彩、密度、材质、图标风格、儿童化程度、可读性与可复用性，选择一套作为全局视觉规则。没有生成能力时，记录不可用原因，并以原创 SVG / Godot 2D 绘制、可编辑插画替代；不能假称已生成。
3. 基于选定风格，真正产出可用于游戏的**透明背景精灵、主题装饰、图标、卡片插画、背景小组件与切水果前/后两态资源**。生成出的“整张参考截图”不算已完成可用素材。
4. 对原始生成图执行**透明度/边缘/裁切/比例/颜色/纹理一致性**检查；去除伪文字、残缺肢体、莫名漂浮物、光源不一致和风格漂移；必要时分层重绘并优化成 2D 素材。
5. 在真正规模的 Godot 场景中查看最终像素效果，检查不同屏幕的缩放锯齿、压缩、纹理大小和内存占用。**必须以游戏内实测截图审美决策，而不是以单张 AI 概念图决定效果好坏**。
6. 保存可追溯的素材记录：来源、生成模型/工具（若可知）、提示词或风格摘要、后期处理、采用/未采用原因、许可情况，写进 `docs/ASSET_PROVENANCE.md`。不得上传未经授权的第三方艺术资源。
7. 可借助已有的设计/可视化质量技能审核，但只有它们在本地真的存在时才调用；**禁止编造技能、伪造执行结果或调用不存在的外部 API**。

### 4.3 视觉必须做出来的细节

- **触摸反馈**：手指按下有真实按压缩放，松开略回弹；拖动和滑动无明显滞后。
- **物理反馈**：水果柔软碰撞、泡泡黏附和破裂、蛋糕切边掉落、弹珠火花与砖块微震、图块三连飞走、麻薯蓄力压缩/空中拉伸/完美落地回弹、2048 缩放合并、果冻剖开与果汁颗粒。
- **动效节奏**：常规点击约 100–220 ms，通关庆祝约 250–600 ms；有意义的运动优先，无意义的全屏运动减到最少；任何动效不得妨碍迅速重开。
- **音频**：低刺激、木琴/玻璃/水滴/轻弹跳类型；连击音阶逐渐上扬，避免噪声尖峰；统一响度。音乐不是强制的，但绝不能使用未经许可的商业音乐。
- **文字与可读性**：按钮文字完整、数字清晰、提示简短；所有复杂背景上的字有稳定对比度，不因背景色变化看不清；无乱码、缺字和图片内生成的伪文字。
- **布局**：小屏与高长宽比屏幕中，顶部成绩、主玩法区域、底部操作条都可见且易触达；系统状态栏与导航手势区域不会挡住按钮。
- **性能约束**：粒子与精灵复用、对象池、贴图图集/压缩、场景卸载、限制过度绘制；不能牺牲运行流畅度换高密度特效。

### 4.4 视觉验收过程

至少保存并认真检查以下视觉样张：启动/首页、八款游戏各自**真实运行中**、暂停/结算、设置页面，以及一组小屏长屏的适配截图。对每张检查：元素对齐、留白、颜色、按钮触控范围、字体、截断、被遮挡、风格一致性、动画前后状态。将发现的问题**批量整理—批量修复—复验**；不要只生成素材后跳过运行时验证。整体验收阶段集中做两轮完整视觉复核；若仍有阻断缺陷，修复并复测相关项，但不要无终点地追求主观微调。

## 5. 项目执行阶段与不可跳过的门禁

### Phase 0 — 现场调查、风险审计与目标锁定

- 输出当前路径、目录结构、Git 状态、现有分支/远端、已安装工具及版本、GitHub 身份/权限状态、可用图像技能、Android SDK/JDK、连接设备或模拟器状态。
- 明确用户指向的是哪个目录，不得创建在其它位置；遇到现有未提交修改要保留、区分和隔离，不得覆盖。
- 核对八款玩法风险，特别标记：多球倍率导致的性能风险、三张消除的可解性风险、泡泡龙的悬空连通性、麻薯跳台可达性与落点判定/按压中断、2048 合并语义、AI 素材风格漂移、签名密钥和 Android 真实安装。
- 建立 `docs/AUDIT.md`、`docs/IMPLEMENTATION_PLAN.md`、`docs/DECISIONS.md`、`AGENTS.md`（仅在适合时），含负责人（当前 Codex）、执行顺序、验收证据、阻断等级。
- **门禁**：目标仓库确定；风险有方案；不破坏现有数据；可执行的环境缺口已列明。

### Phase 1 — 初始化 Git、结构与安全的远端仓库

- 如当前不是 Git 仓库，在当前项目根目录 `git init`，配置 `.gitignore`（Godot 缓存、Android/Gradle 缓存、本地 `dist`、签名库与凭据、日志等），初始提交 README 与工程骨架。
- 如果已有 Git：尊重其历史、默认分支、origin 和远程内容；不要重新 `git init` 破坏已有提交，也不要覆盖已有 README/文件而不审计。
- 通过 `gh auth status`/`gh api user` 确认**真实 GitHub 身份**。若没有 origin，创建 `Mellow-Pocket` 或用户指定名称。**未明确指定公开可见性时，新仓库默认 `private`**，不擅自将用户项目公开。
- 参考命令仅用于合适前置条件、不要机械执行；**优先提供 Windows PowerShell 可执行的脚本，同时保证 CI 中的 Linux Shell 命令独立正确**：

```bash
# 仅当当前目录已确认是目标项目、已有初始提交、没有已有 origin 时：
gh repo create Mellow-Pocket --private --source . --remote origin --push
# 后续提交使用普通 push，绝不以 force push 修复失配
```

- 确保默认分支有 upstream；校验 origin URL 和账户正确，远端项目不是另一个人/另一个应用的仓库。
- 完成基本 GitHub CI 工作流雏形，并尽早首次推送，后续按照阶段做有意义的提交，减少断线丢失进度。
- **门禁**：本地正确、有回滚点，远端属于预期账号且内容与初始提交一致；失败时可继续本地开发，但禁止声称远端已就绪。

### Phase 2 — 锁定美术设计系统、主菜单与早期 Android 试运行

- 出 `docs/PRODUCT.md`、`docs/DESIGN_BIBLE.md`：色彩 token、字体、间距、按钮、粒子、音效、动画、图标、卡片和八个游戏主题映射。
- 按第 4 节先使用**真实可用**的 AI 图像生成技能（如存在）生成参考与一批生产素材，选定整套视觉世界。
- 实作 Home、GameShell、Settings、八张完整入口卡片、基本导航和统一存档/音频接口。
- 此时**尽早做一次 Android 调试版安装**，验证真实屏幕尺寸、触控输入、安全区、返回键和中文字体，别到全部游戏写完才发现移动端布局不适用。
- **门禁**：首页美观且八个入口存在；可用真实触屏进入/返回；截图实测无严重裁切；视觉原则已经统一。

### Phase 3 — 两款纵向切片：Cake Stack + Number Bloom

- 先完成开发风险较低、最能展示基础交互的 Cake Stack 和 2048，从首页入口到真实玩法、纪录、音效、结算、重开、退出完整贯通。
- 这里必须建立各项测试和截图能力，验证共用系统。**不要在基础接口没稳定之前同时散乱创建八套代码**。
- 做首次认真 UI/UX 反馈修正，统一触控感、字体、动画与分辨率策略。
- **门禁**：两款游戏在 Godot 中能真实游玩，多次重启/切换正常，主要规则自动测试通过。

### Phase 4 — 逐款完成其余六个游戏

建议顺序：`Fruit Drop → Bubble Garden → Mochi Hop → Tile Trio → Bouncy Balls → Jelly Slice`，可基于实际风险微调。**每做完一款，立即完成以下全部项目，然后再做下一款**：

1. 真实可玩循环，不是标题、界面或单关示例。
2. 玩法级边界情况与自动化规则测试。
3. 原创美术、动效和音效已接入真实场景。
4. 首页 ↔ 游戏 ↔ 结算 ↔ 重开的完整流程测试。
5. 至少一次实际操作/自动手势运行和截图审查；如果当前无法真机运行，记录仍待 Android 门禁验证。
6. 无新引入的 P0/P1 缺陷，已有其他场景回归测试通过。
7. 一次有意义的 Git 提交，并适时推送远程检查点。

**门禁**：八款均为完整游戏，无未实现入口；所有必须功能有证明；没有用降低游戏数来“提前完成”。

### Phase 5 — 全量深入审计与修复

至少覆盖：

- **规则**：得分、连击、胜负、计数、碰撞、失效事件、随机种子、可解性、超时/暂停、重试、存档、返回、线程/信号/计时器生命周期。
- **边界**：连续 30 次切换游戏、反复返回、快速乱点、密集滑动、双指误触、动画中退出、后台恢复、突然重启、空存档、损坏存档、重复初始化、无效输入。
- **专项压力**：弹珠球数上限与持久高速碰撞、泡泡悬空大面积掉落、水果连锁合并、切水果高速划线、2048 满盘多步验证、Tile Trio 不同种子和托盘极端情况、Mochi Hop 蓄力长短边界/中断取消/平台生成可达性/跳跃与落点一致性/连续完美分数。
- **视效**：逐页观察实际截图，修复场景风格不一、文字错误、空白区、屏幕挤压、视觉层级混乱、颜色对比不足、触控不可达等问题。
- **性能**：Android 启动、切关和高负载模式的帧时间、峰值节点/物体数、内存压力、粒子峰值与掉帧原因；优先减少不必要的渲染/物理开销。
- **安全与版权**：检查源码、日志、资源和 Git 历史，不得出现 signing secrets、个人令牌、未获许可素材或任意危险权限。
- **仓库**：README 准确、文档不堆砌、无无用缓存/调试截图污染、无死代码、无忘记删除的假场景、无失效路径和不可重现构建指令。

测试要求：

- 用 Godot headless 模式创建可**真正执行且返回正确退出码**的规则测试；不能只放空测试文件。
- 为各游戏提供可复现的种子与关键操作序列；Tile Trio 的程序化关卡需用求解器批量验证可解性；Mochi Hop 的程序化跳台至少批量抽测 1000 个固定种子或等效的大样本集合，验证目标平台的可达蓄力区间与实际落脚区域。报告样本数量、失败种子及可复现的判定方法。
- 提供自动化冒烟测试覆盖八个场景的初始化、必要输入、返回及重开；对不能在无头环境执行的触控/视觉项，用模拟器/设备真实执行并记录证据。
- `docs/QA_REPORT.md` 包含测试时间、环境、命令、用例数、PASS/FAIL/SKIP、失败复现与修复证据；不得用一个“all good”代替。

缺陷优先级：`P0` = 崩溃、无法安装、严重数据丢失、直接无法玩；`P1` = 核心规则错误、必现软锁、主要按钮不可点、明显破坏视觉/性能体验；`P2` = 一般体验瑕疵；`P3` = 低优先级装饰。**正式 Release 前 P0/P1 必须为零，阻断性 P2 必须修复；未解决的非阻断项要公开记录，不能冒充零问题。**

### Phase 6 — 有限但扎实的审美与手感迭代

- 第一轮在 Phase 3 阶段基于真实运行画面，统一基础界面与交互规范。
- 第二轮在八款全成后，**集中审查所有页面与代表性高负载操作**，形成一份批量修改清单，优先修复重大不协调与手感问题。
- 第三轮执行针对性复核：聚焦前一轮发现的问题，修复必要剩余瑕疵，不做无根据的全面重写。
- 验收时至少核对：首页八张卡片是否值得点；每款开场 5 秒能否理解；每个触控反馈是否令人满意；玩法区域是否有足够空间；背景是否喧宾夺主；连击是否爽但不刺眼；整体是否明显出自同一套设计系统。
- **视觉不合格时宁可替换个别素材、简化多余装饰、统一动效，不要堆更多杂乱视觉元素。**

### Phase 7 — Android APK、签名与真实安装测试

1. 检查官方 Godot export templates 与编辑器版本匹配，生成正式 `export_presets.cfg`，不让敏感明文密码进入 Git。
2. **实际导出可安装的 APK**。稳定 Release 优先使用安全保存的正式 release keystore，不能拿 `debug` 签名 APK 伪装成可长期更新的正式发行包。签名文件必须保存在仓库外且权限受限；使用环境变量/合适的系统凭据能力注入密码，不在代码、日志、GitHub Actions 日志和 Git 历史中留下明文。
3. 若本地没有可持续安全保管的 signing key，可在受限本地安全位置生成并记录证书指纹，确认后续升级可复用；如果无法安全保存/获取密钥，**该项标记 BLOCKED，不发布“正式稳定版”**。不需要把密钥发给用户或上传到 Release。
4. 使用 `apksigner`/`aapt`/相关 SDK 工具验证 APK 签名、包名、版本号、SDK/ABI、主要权限；输出 SHA-256。
5. 使用当前可用的 Android 真机或模拟器：通过 `adb install` 真实安装，通过启动命令打开，完整点击八个游戏、暂停、重启、切换、返回、后台恢复，采集运行日志和实际截图。**只有模拟器时如实标注模拟器验证；不要谎称真机验证。**
6. 实测至少一种常见手机竖屏；可选再用大屏/平板与更长窄屏验证。不能仅使用桌面窗口截图冒充 Android 截图。
7. 性能目标：普通 Android 设备优先稳定接近 60 FPS；中等负载下尽量维持 55 FPS 以上；以真实测量帧时间、卡顿和内存为依据，记录设备型号/模拟器规格。模拟器不能作为真实设备性能结论。
8. 应用冷启动、八个入口、最高负载弹珠/切水果、音频、返回、恢复、重装后的存档策略与启动图标全部正常。
9. APK 体积尽量合理，建议将 `100 MB` 作为**优化参考目标而非盲目一票否决**；不要为了压缩体积牺牲明显视觉质量。

**重要门禁**：没有成功在 Android 真实系统（真机或模拟器）安装并启动、没有触控与场景验证证据，不能叫“已验证可用的正式 APK”，也不能发布稳定版。如果环境完全无 Android 运行条件，完成能做的工作、保留工程和构建产物，准确报告实际阻断。

### Phase 8 — CI、最终审计与远端完全同步

- 提供可信的 GitHub Actions：至少检查 Godot headless 导入、规则/冒烟测试和可以自动验证的 Android 构建环节。固定工具版本，减少隐藏依赖；上传必要日志/测试产物，不把签名凭据泄露进工作流。
- 最终运行真实测试、静态代码审计、素材来源审计、Godot 工程导入检查、Android 安装验收，修复所有发布阻断项。
- 清理不需要的缓存、临时文件、错误的导出产物、未用资源、示例密码、意外提交的密钥；**不能粗暴删除用户原始文件或 Git 历史**。
- 补齐全英文、设计美观但信息准确的 `README.md`：项目定位、八款游戏、精选真实截图、Android 安装说明、构建条件、测试方法、目录结构和 GitHub Release 下载方式。请使用简洁英文，不要混入中文 README 内容。
- `git status --porcelain` 应为空；`git fetch` 后检查本地 `HEAD`、upstream 和远端默认分支指向相同提交，不允许未提交变更或忘记推送的本地 commit。
- 查看 GitHub Actions 的最新运行结果（例如 `gh run list`、`gh run view`、`gh run watch`），确保**同一个最终 commit SHA** 的必要检查均为成功。若远程 CI 失败，定位修复并重新推送，绝不以本地成功替代远程状态。
- **门禁**：本地和远端代码完全一致，CI 绿灯，发布记录与最终构建 SHA 对应，所有 Release 阻断项解决。

### Phase 9 — 创建 GitHub Release（仅当以上全部通过）

1. 确认最终稳定版本（建议首次版本 `v1.0.0`，但实际依已有 tags 决定，**不覆盖已有 tag**）。生成由**该最终 commit** 打包的经过验证的签名 APK。
2. 生成 `SHA256SUMS.txt` 和真实 `release-notes.md`，说明八个游戏、安装、支持范围、构建 SHA、测试结果与限制。
3. 创建**附带提交信息的 Git tag** 并正常推送；验证 tag 指向的提交正是 CI 检查通过的提交。
4. 先创建 **draft Release**、上传 `Mellow-Pocket-vX.Y.Z.apk`、`SHA256SUMS.txt`、必要的发布说明。参考官方 CLI：

```bash
# 以下变量与路径必须按实际验证结果替换；只示意安全流程：
git tag -a v1.0.0 -m "Mellow Pocket v1.0.0"
git push origin v1.0.0
gh release create v1.0.0 dist/Mellow-Pocket-v1.0.0.apk dist/SHA256SUMS.txt --verify-tag --draft --title "Mellow Pocket v1.0.0" --notes-file release-notes.md
```

5. 核对草稿附件、大小、校验值、版本和 tag。使用 `gh release download` 下载已上传 APK 到独立临时目录，重新计算 SHA-256 与本地 APK 对比，确认实际上传字节一致；再次检查安装包签名。
6. 一切正确后，将草稿正式发布（如 `gh release edit v1.0.0 --draft=false`），然后再次检查 Release 页面、下载链接、资产列表、版本、`origin` 与 `git status`。
7. **一旦有正式 Release，不得为了修复问题而偷偷移动已发布 tag、force push 或静默覆盖版本资产**；发现实质性缺陷应走新的补丁版本并留下变更记录。
8. 如果仓库为 private，Release 也仅对有该仓库访问权限的人可见；不得以“需要让所有人下载”为由自行改成 public。

## 7. 工作方式、迭代纪律与恢复机制

- 在 `docs/IMPLEMENTATION_PLAN.md` 保持一个短小清晰的阶段看板：`TODO / IN_PROGRESS / PASS / FAIL / BLOCKED`，记录当前阶段、最近一次通过测试的 commit SHA、下一步动作。
- 每完成一个明显阶段就做小型审计、运行已有回归，**按功能里程碑提交 Git**；避免一天后一次性大提交，或无限堆叠未验证修改。
- 问题优先级始终是：`无法安装/启动 > 数据与玩法正确性 > 挡住操作的视觉问题 > 性能严重退步 > 美术不统一 > 细枝末节`。
- 在修复某项问题时优先采用最小但完整的改动，不为修一个特效重写八个游戏公共系统。
- 测试失败先复现、定位、修复、回归；不通过删除测试、放宽正确性断言、捕获全部异常静默忽略等方式制造“PASS”。
- 审计出新问题时记录影响/修复价值/复现条件，优先处理真正影响玩法、流畅度、审美与交付的项，避免无收益的架构重构。
- 设计审美迭代以**关键截图批量审查 → 集中修复 → 重点复验**为主，避免没有终点的重复润色。要求高标准，但每轮都必须提供具体改善证据。
- 当会话/上下文即将中断时，更新 `docs/IMPLEMENTATION_PLAN.md` 与 `docs/QA_REPORT.md`，包括做过什么、当前 Git SHA、已验证项、未解决问题、接下来准确动作；让下次 Codex 可直接接续。**不要承诺离开会话后仍会在后台运行**。
- 如果因客观限制必须停止：提交所有安全且经过检查的增量，保持清晰本地状态；列出已完成、未完成、阻断原因和人工必须补充的最小动作；不要把 `BLOCKED` 说成 `DONE`。
